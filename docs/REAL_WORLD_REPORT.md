# ABW-B 실제 정수 워크로드 실용성 검증

최종 판정: **B. 적용 범위를 제한해 공개**

현재 구현을 범용 정렬 라이브러리로 발전시킬 근거는 부족하다. 공개 실제 데이터3종의9개 컬럼 중 Covertype 고도와 Census 산업 코드에서는 모든 비교 구현보다5% 이상 빠른 결과가 세 프로세스 세션 모두에서 반복됐다. 이 두 적용 사례와 고정 소스·재현 자료를 한정해 공개할 근거가 있다. 나머지 컬럼의 최선 구현 대비 성능과 회귀를 함께 보존한다.

연구 지속을 위한 추가 휴리스틱이나 최적화를 만들지 않았다. 이 판정은 현재 입력과 환경에 대한 검토 결과이며, 재현 스크립트가 미래 실행에 같은 판정을 자동 부여하지 않는다.

## 1. 기존 자료 및 구현 고정

사용자가 지정한 자료는 모두 확인할 수 있었다. 사전 설계에 존재 여부와 해시를 기록하고 원문을 evidence/에 복사했다. 누락 자료를 추측해 보완하지 않았다.

| 확인 자료 | 확인 내용 |
|---|---|
| sort_experiment_M.cpp 및 M_summary.json/M_report.md | 원본 E_pdq 정책·버킷 정렬, M의 전체 검증 범위와 한계 |
| 기존 E_pdq/B 구현 | 직전 swap 소스의 알고리즘 prefix를 그대로 사용. A 경로는 비교·결합하지 않음 |
| B 구조적 최적화 full 보고서 | 일반14종 평균 개선, 직접 출력 효과와 혼합 반례 회귀 |
| 희귀값 교환 배치 보고서 | 동일 multiset에서 늦은 발견 부담과 시간 변동 예외 |
| B 어셈블리 검토 보고서 | 실제 GCC13.3 바이너리의 원본/검사/발견 후 집계, 단순 루프 변경 보류 |

이번 실행에서 분할 정책, 표본 위치, 엔트로피 기준, 버킷 수·비트 선택, 대표값 검사, 혼합 발견 후 경로를 변경하지 않았다. 원본의 대표값0초기화도 유지했다. 이전 실험의 결과와 이번 수치를 합쳐 평균이나 독립 표본 수를 늘리지 않았다.

## 2. 실제 데이터 출처와 추출

아래 컬럼 선정과 전체 파일 사용·순서 보존·예외 처리·메모리 제한은 성능 측정 전에 design_preregistered.json에 고정했다. 적합한 실행 결과를 얻기 위해 입력을 선택하거나 바꾸지 않았다. 합성14종은 별도 회귀 점검으로 구분했다.

### NASA HTTP 로그

출처: [Internet Traffic Archive의 NASA-HTTP](https://ita.ee.lbl.gov/html/contrib/NASA-HTTP.html), [1995년7월 전체 원본](https://ita.ee.lbl.gov/traces/NASA_access_log_Jul95.gz). KSC NASA 웹 서버의 실제 HTTP 요청 기록이다. 게시자는 자유로운 재배포를 허용하며, 일반적인 트래픽 패턴 이외의 분석을 삼가도록 명시한다. SPDX 이름을 가진 별도 라이선스는 확인되지 않았다. 호스트나 요청 문자열을 분석용 배열에 포함하지 않았다.

원본1,891,715행을 끝까지 읽었다. HTTP 상태와 타임스탬프는 각각 파싱 가능한1,891,714행을 원래 순서로 사용했다. 응답 바이트 수는 숫자인1,871,988행을 사용하며 누락 기호와 파싱 불가19,727행을 제외했다. 다른 컬럼의 값을 바이트 누락에 맞춰 함께 삭제하지 않았다. 타임스탬프는 게시된 -0400 오프셋을 적용해 정확한 Unix 초로 변환했다. 원래 해상도1초를 줄이지 않았다.

### Covertype

출처: [UCI Covertype](https://archive.ics.uci.edu/dataset/31/covertype), Jock Blackard,1998, DOI10.24432/C50K5N, **CC BY4.0**. USFS/USGS 자료에 기반한 실제 산림·지형 데이터다. `covtype.data.gz` 전체581,012행에서 Cover_Type, Elevation, Horizontal_Distance_To_Roadways를 숫자 그대로 추출했다. 고도·도로 거리는 미터이며 순서·크기·중복도를 변경하지 않았다.

### Census1990 공개 가공본

출처: [UCI US Census Data1990](https://archive.ics.uci.edu/dataset/116/us+census+data+1990), Meek·Thiesson·Heckerman,2001, DOI10.24432/C5VP42, **CC BY4.0**. 실제 인구조사 PUMS 자료의 공개 가공본이다. 제공기관이 이미 행을 무작위화하고 일부 변수를 재코딩·이산화했다. 원시 인구조사 컬럼 그대로의 실험으로 부르지 않는다.

`USCensus1990.data.txt` 전체2,458,285행에서 caseid, dIndustry, iSex를 추출했다. 공개 파일 순서와 제공된 코드를 유지했다. caseid는 공개본의 관리용 ID이며 이 파일에서는 오름차순이다. 실제 개인 식별이나 분석의 대상으로 사용하지 않았다. NASA 타임스탬프도 이미 오름차순이며 두 입력 모두 그대로 사용했다.

## 3. 비교 구현

모든 비교는 **정수 키 배열 자체의 비감소 정렬**이다. stable 정렬이나 키에 연결된 행·payload 이동은 검증하지 않았다. 전체 정렬 결과를 독립 NumPy 정답 배열과 원소별로 일치 검사했다.

| 구현 | 조건 |
|---|---|
| pdqsort | Boost1.90.0의 pdqsort, uint32 |
| E_pdq | 기존 선택 정책과 원본 분배/내부 pdqsort |
| ABW_B | 고정된 기존 B, 정확 단일값 버킷 직접 출력 |
| Boost Spreadsort | Boost1.90.0 integer_sort, uint32 |
| CAFS_u32 | 공식 cafs2::cafs_sort, uint32 스칼라 버킷 경로, pdqsort fallback |
| CAFS_i32 | 같은 값의 int32 배열, 공식 SIMD 경로, pdqsort fallback |
| Counting | 아래 공개한 min/max 기반 dense histogram 구현 |

CAFS는 [공식 저장소](https://github.com/kexibq-official/cafs-lib)의 고정 commit `13488afef446ae88e7ad631ec6f862def896094a` 소스와 MIT 라이선스를 확보했다. 두 헤더를 수정하지 않고 빌드·정확성 검증을 통과했다. 공식 API의 fallback 인자로 동일 Boost pdqsort를 사용했다. 기본 std::sort fallback과 다른 설정임을 명시한다.

공식 uint32 경로는 지원되며 스칼라다. SIMD 특화가 있는 int32도 따로 시험했다. 이번 실제 값은 모두 int32에 정확히 표현 가능하다. 입력을 준비할 때 정수값을 보존해 int32 벡터를 만들고 동일한4바이트 원소로 정렬했다. uint64로 넓혀 비교하지 않았다. i32 준비는 다른 방법의 입력 복제와 마찬가지로 타이머 밖이다. 원래 u32 버퍼를 그대로 정렬해야 하는 API에는 CAFS_u32 결과를 사용해야 하며, i32 결과만으로 u32 성능을 주장하지 않는다.

CAFS가 C++20·AVX2·BMI1을 요구하므로 **모든 비교군**을 동일 `clang++ -std=c++20 -O3 -DNDEBUG -mavx2 -mbmi -static -pthread`로 빌드했다. E/B 소스는 그대로다. 이전 GCC13.3/C++17 Colab 결과와 컴파일 조건이 다르므로 수치를 합산하지 않았다.

Counting은 함수 안에서 min/max를 구한 뒤 `range=max−min+1`개의 uint64 count를0초기화하고 집계·순서대로 fill한다. 추가 힙은 정확히8×range 바이트다. 함수 실행에 min/max·할당·초기화·집계·출력·해제를 모두 포함한다. 64MiB 이하인 경우만 실행하도록 성능 측정 전에 기준을 고정했다. 이번 실제9개에는 모두 적용 가능했다. 합성 입력에서 제외된 경우와 지원 안 되는 i32 값 범위는 manifest의 methods에 남겨뒀다.

Counting은 직접 구현한 단순 단일 스레드 대조군이며 소스를 공개한다. schema가 제공하는 사전 범위, 재사용 작업 버퍼, 별도 고도 최적화된 히스토그램 구현의 성능을 대표하지 않는다. 그런 변형을 추가 개발하거나 성능에 맞춰 선택하지 않았다.

## 4. 측정 환경과 검증

- CPU: Intel(R) Core(TM) i5-14500; 논리 CPU20개, 물리 메모리31.75GiB.
- 운영체제: Windows-11-10.0.26200-SP0.
- 컴파일러: LLVM-MinGW clang23.1.5, libc++/UCRT. 상세 버전·경로·명령·실행 파일 해시를 environment.json/build.json에 기록했다.
- 상속된 affinity의 가장 낮은 논리 CPU0에 고정했다. turbo·백그라운드 작업을 제거하거나 CPU 주파수를 고정하지 않았다. P/E 코어 매핑도 별도 측정하지 않았다.
- 실제9개는 입력별 새 프로세스3개에서 실행했다. 각 프로세스에서7방법을7회씩 교차 실행해 방법별로 각 실행 위치를 정확히 한 번 거쳤다. 프로세스 내 같은 입력 배열을 복제해 쓰며, 원본 입력·정답 파일은 동일했다.
- 입력 순서는 고정 난수로 무작위화했다. 고정된 소규모 warmup을 공통 적용하고, 파일 IO·입력 복제·warmup·정답 비교·로그 기록은 정렬 타이머에서 제외했다. 기존 분석과 모든 정렬 소유 할당·초기화·분배·내부 정렬·복사·해제는 포함했다.
- 실제 데이터 본 정렬1,323회, 합성 회귀3,681회로 총5,004회다.153개 입력/세션 프로세스의 출력 전체가 정확했다. 별도 메모리 프로세스288개도 정확성을 통과했다. 사전 검사와 warmup은 이 본 정렬 수에서 제외했다.
- 메모리 측정은 별도 빌드의 전역 C++ new/delete와 CAFS aligned allocation을 계측했다. 입력·정답·정렬용 입력 복제 이후의 요청 힙 최대 동시량이다. allocator metadata·CRT 내부 비공개 malloc·스택은 포함하지 않는다. 소스에서 확인한 주요 작업 배열 할당은 이 경로로 잡았다. 계측 비용을 본 시간에 넣지 않았다.
- 프로세스 working set 현재값/최대값도 기록했다. 최대값 증가분은 페이지·기존 peak·상주 상태에 영향을 받으며 정확한 힙 사용량과 다르다. 그 값을 그대로 추가 메모리라고 해석하지 않는다. 요청 힙0은 스택까지0이라는 뜻이 아니다.
- 모든 입력 해시를 측정 뒤 재검증하고 NumPy 정답을 다시 생성해 확인했다. E/B 선택과 B 발동 여부는 별도 버킷 감사와 모두 일치했다.
- 이번 실제 데이터의 다른 CPU 실행은 수행하지 않았다. 같은 머신의 세 세션을 독립 하드웨어 검증으로 세지 않는다.

### 전체 승패와 기하평균

사전에 정한 ±5% 시간 차이를 기술적 동률 구간으로 사용한다. 통계적 유의성이나 신뢰구간은 아니다. 각 입력에서 같은 세션끼리 시간비를 구해 세 세션의 중앙값을 취했다. 속도비는 기준 시간/B 시간이며1보다 크면 B가 빠르다. 아래 기하평균은9개 컬럼에 같은 가중치를 준 값이며, 같은 데이터셋의 컬럼을 독립 표본으로 가정한 모집단 추정이 아니다.

| E_pdq | 3 | 6 | 0 | 1.277× |
| spread | 7 | 0 | 2 | 1.940× |
| CAFS_u32 | 3 | 0 | 6 | 0.821× |
| CAFS_i32 | 3 | 0 | 6 | 0.746× |
| counting | 8 | 0 | 1 | 2.023× |

pdq 대비 기하평균1.429배가 모든 특화 정렬기보다 우수하다는 뜻은 아니다. CAFS_u32 대비0.821배, CAFS_i32 대비0.746배로, 평균적으로 각각약21.8%,34.1% 더 긴 시간이 걸렸다.

### 회귀와 예외값

모든 세션 관측을 남겼다. 실제 입력의 최대 pdq 대비 회귀는 Census 성별 코드 세션1에서 B3.4443ms / pdq2.1301ms = **+61.7%, +1.3142ms**다. 이 입력의 세션2·3에서도 B는 pdq보다 느렸다. 시드·입력을 바꿔 회귀를 없애지 않았다.

| 세션 | Census 성별 pdq(ms) | E(ms) | B(ms) |
|---:|---:|---:|---:|
| 1 | 2.1301 | 2.5711 | 3.4443 |
| 2 | 2.2445 | 2.5799 | 2.6651 |
| 3 | 2.1901 | 2.6128 | 2.5902 |

이 입력은 B의 대표값 검사 루프에 들어가지 않았다. 원본 E의 분석 후 native 폴백에도 부담이 존재하며 B와 E 사이의 변동도 있다. 최대 회귀 전체를 B의 검사 비용으로 부르지 않는다.

## 6. 직접 출력이 없는 경우

직접 출력은 실제9개 중 **2개**, 해당 B 본 호출189회 중42회에서 발동했다. 이것은 사용 빈도나 확률 추정이 아니라 선정한9개 컬럼의 횟수다.

직접 출력이 없는7개 중 실제 분배까지 수행한 것은 도로 거리1개다. 최초 혼합 index4에서 검사를 종료했다. 나머지6개는 원래 정책에서 native로 처리돼 대표값 검사 커널을 호출하지 않았다.

| 입력 | 원래 분기 | B−E, 짝지은 세션 중앙값(ms) | B/E 시간 증가 |
|---|---|---:|---:|
| nasa_status | native | +0.0518 | +2.20% |
| nasa_timestamp | native | -0.0729 | -5.00% |
| nasa_bytes | native | -0.1187 | -0.95% |
| covtype_cover | native | -0.0054 | -0.64% |
| covtype_road_distance | active12 | +0.0376 | +1.26% |
| census_caseid | native | -0.0139 | -1.09% |
| census_sex | native | +0.0852 | +3.30% |

도로 거리에서 B가 E에 추가한 시간은 세션 차이 중앙값약0.0376ms, 시간비 기준약1.26%다. B의 추가 요청 힙은 대표값 배열16,384바이트다. native 경로의 양·음 차이는 검사 비용의 인과 효과로 해석하지 않는다. 앞선 희귀값 끝 배치에서 확인한 큰 검사 부담이 실제 입력에서 사라졌다고 주장하지 않는다. 이번 실제9개에는 그런 늦은 혼합 발견 사례가 없었다.

## 7. 추가 메모리와 손익

아래 값은 별도 계측한 최대 동시 요청 힙 바이트다. 입력 배열과 정답 배열은 제외했다. 모든 정렬 소유 계측 할당은 함수 종료 시 해제됐다. 프로세스 전체 working set 기록은 memory.csv에 있다.

| 입력 | E | B | Spreadsort | CAFS_u32 | CAFS_i32 | Counting |
|---|---:|---:|---:|---:|---:|---:|
| nasa_status | 0 | 0 | 2,416 | 24,576 | 24,576 | 2,416 |
| nasa_timestamp | 0 | 0 | 0 | 0 | 0 | 19,052,360 |
| nasa_bytes | 34,600 | 34,600 | 138,288 | 1,380,352 | 1,380,352 | 54,591,496 |
| covtype_cover | 0 | 0 | 56 | 24,576 | 24,576 | 56 |

| covtype_road_distance | 2,422,368 | 2,438,752 | 14,240 | 479,008 | 479,008 | 56,944 |
| census_caseid | 0 | 0 | 0 | 0 | 0 | 19,666,280 |
| census_industry | 9,839,300 | 10,840 | 104 | 24,576 | 24,576 | 104 |

pdqsort의 계측 요청 힙은 이 입력에서0이었다. 두 성공 입력에서는 다음 교환이 관측됐다.

- Covertype 고도: B약80.0KiB, Counting15.6KiB, CAFS약227.8KiB. B는 Counting보다 추가 힙약64.4KiB를 쓰면서 더 빨랐다. 원본 E의2.42MB 임시 작업공간을 피했다.

- NASA 응답 바이트의 Counting 힙은약54.6MB였다. 64MiB 예산 안이어서 그대로 실행했고 느린 결과도 보존했다. 입력 범위에 비례하는 dense histogram의 한계다.

## 9. 핵심 질문에 대한 답

1. **실제 데이터에서도 pdq보다 빠른가?** 그렇다.5% 기준3/9개에서 빨랐고, 고도·산업 코드의 큰 이득이 세 세션에서 반복됐다. 다른5개는 근접 동률, 성별 코드는 회귀했다.
2. **특화 구현과도 경쟁력 있는가?** 고도·산업 코드 두 컬럼에서는 비교한 Spreadsort·CAFS 두 타입·Counting을 모두 이겼다. 전체9컬럼에서는 CAFS보다 느려 범용 경쟁력은 확보하지 못했다.
3. **직접 출력은 얼마나 자주 발동하는가?**9개 중2개, B 본 호출189회 중42회다. 실제 서비스에서의 발생 확률은 측정하지 않았다.
4. **발동하지 않을 때 추가 비용은?** 유일한 mixed 분배 입력에서는 E 대비약1.26%,0.0376ms의 요약 증가가 있었다. 다른6개는 대표값 검사를 호출하지 않았다. 늦은 발견의 이전 반례는 여전히 별개로 유효하다.
5. **추가 메모리가 정당한가?** 두 성공 컬럼의약80KiB·11KiB는 관측된 속도 이득과 교환할 현실적인 규모다. 혼합 도로 거리에서는 더 빠르고 메모리도 적게 쓰는 대안이 있어 정당화하기 어렵다.
6. **어떤 입력에서 사용하는 것이 합리적인가?** 현재 그대로의 Covertype 고도·Census 산업 코드와, 별도 재현 검증으로 같은 이득을 확인한 동등한 키 전용 배치 작업이다. 고유값 수만으로 다른 입력을 추천하지 않는다. 현재 정책이 같은 값 범위나 입력 크기에서 다른 분기를 선택할 수 있다.

## 10. 한계와 최종 판정

**B: 적용 범위를 제한해 공개.** 공개할 범위는 고정 후보 소스, 두 실제 성공 사례와 실패 사례, 입력 추출 코드, 원시 측정 및 재현 절차다. 범용 정렬기의 대체재나 독립 라이브러리 개발로 확장하는 A 판정은 지지하지 않는다. 서로 다른 두 실제 컬럼에서 강한 대안을 이긴 결과가 반복됐으므로 실용적 이득이 없다는 C 판정도 현재 자료와 맞지 않는다.

- 실제 데이터는3개 공개 자료,9개 관련 컬럼뿐이며 생산 시스템의 작업 빈도 분포를 대표하지 않는다.
- 실제 배열의 최대 길이는약246만이다.1,000만 실제 입력은 확보·측정하지 않았으며 복제로 만들어 채우지 않았다.
- 실제 데이터는 모두 비음수이며 i32/u32에 들어간다. 음수·전체 uint32 범위·부착된 payload·stable sort는 검증하지 않았다.
- Census는 제공기관이 가공한 공개본이고 ID는 정렬돼 있다. raw PUMS 순서나 임의 ID 입력으로 일반화하지 않는다.
- 한 i5 Windows 환경의 세션 반복이다. 이전 Xeon 결과는 다른 합성 실험이며 이번 실제 입력의 두 번째 하드웨어 재현이 아니다.
- 단일 스레드·매 호출 작업공간 신규 할당·warmup된 in-memory 입력 복제 조건이다. schema 정보가 있는 Counting, 작업공간 재사용, 다른 특화 구현·컴파일러·CPU에서 순위가 달라질 수 있다.
- ±5% 승패는 기술적 분류이며 통계적 유의성 검정이 아니다. 개별 반복의 변동과 큰 회귀를 제외하지 않았다.
- B의 정책이나 알고리즘을 수정하지 않았다. 부정적인 입력을 고치기 위한 후속 휴리스틱·최적화·임계값 탐색을 자동으로 시작하지 않는다.

## 11. 공개 저장소의 원시자료와 재현

공개본에서는 경로 설명을 저장소 구조에 맞췄다. 수치와 판정은 원래 실행 기록 그대로다. `benchmarks/results/raw/`에 원시 JSONL을 보존하고 CSV·검증 메타데이터도 함께 제공한다. 실제 원본 데이터와 실행 파일은 저장소에 넣지 않는다. 고정 소스와 해시 검증 다운로드·추출·빌드·실행 절차는 [벤치마크 README](../benchmarks/README.md)에 있다.

`include/abw/abw.hpp`는 API를 정리한 헤더다. 위 성능값은 고정된 기존 벤치마크의 결과이며 공개 헤더를 별도로 성능 측정한 결과가 아니다. 공개 헤더의 선택·비트 구간·직접 출력 판단·정렬 결과는 고정 원본과 비교해 검증했다.
